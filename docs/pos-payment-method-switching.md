# Switching an unpaid POS checkout between card and QR

The cashier can request another payment method without deleting the basket. Both Card → QR and QR → Card use the same queued switching flow. Method selection remains available while payment is pending; starting another payment and finalizing the sale remain blocked until the previous request settles. Repeated clicks during cancellation cannot start overlapping cancellation requests.

- Before card authorization is dispatched, switching cancels the local preflight and opens the requested method without charging the terminal.
- After card authorization starts, switching checks the original attempt. Push ECR also receives its supported cancellation request. Minu's current integration has no implemented Agent cancellation endpoint: the cashier must cancel on the physical terminal. The pending attempt is retained and checked until an explicit decline/cancellation or approval arrives. Closing its waiting overlay is not cancellation. Unknown terminal codes, insufficient-balance messages without a verified final status, and network failures cannot release the attempt.
- Minu authentication completes before creating a payment or reserving terminal/stock. A login outage returns `CARD_PAYMENT_NOT_STARTED` and can be retried. A lost invoice response remains financially unknown: the original invoice is polled automatically, without sending another charge. Before rejecting a new request because of an older pending payment, the API refreshes that original invoice. A confirmed refusal releases it automatically; a late approval stops that new request. Concurrent requests still serialize and recheck the terminal in the database. No cashier unlock action is required or exposed by this flow.
- Automatic cancellation after an unknown outcome requires a documented provider cancellation operation and a definitive result for the original invoice. This integration does not infer cancellation from a timeout, API-level error, missing RRN, or elapsed time. It must not report failure and resend while the original debit may still complete.
- For QR, switching calls the existing cancellation API with `requireProviderCancellation: true`. The server must confirm provider cancellation. Merely expiring or abandoning the local checkout after a failed provider cancellation is insufficient. An already abandoned invoice must be cancelled with the provider on retry; it cannot use the legacy local-release shortcut.
- If the old payment is approved while switching, it stays attached to the basket. A fully paid basket is completed normally; another full payment is not opened. Confirmed partial payments are preserved, and the requested method can pay only the remainder.

The selected method opens after cancellation; the cashier then starts the new payment normally. A page refresh retains the existing payment recovery reference but not the desired next method. The cashier can select the desired method again.

Deploy API before Vendor. Old clients keep the existing cancellation behavior because the stricter option is opt-in. A newer Vendor refuses to switch if an older API does not return explicit provider cancellation confirmation. No schema migration or payment credential changes are needed.

Tests cover both directions, cancellation failure, approval during cancellation, partial payments, an in-flight authorization without a rendered entry, strict provider cancellation policy, and the rendered enabled/disabled method controls. Live terminal cancellation must still be verified with Minu; no real payment is generated by these tests.
